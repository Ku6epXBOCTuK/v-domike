# Правила работы

Устройство кода — [`docs/architecture.md`](docs/architecture.md), оформление и
тексты — [`docs/design.md`](docs/design.md), команды —
[`docs/development.md`](docs/development.md), что не сделано —
[`docs/backlog.md`](docs/backlog.md). Противоречишь документу — сначала меняешь
документ.

## Перед коммитом

```sh
pnpm check && pnpm lint && pnpm test
```

## Работа по шагам

Одно изменение за раз. После шага — короткое саммари и остановка, ревью делает
владелец. Не коммитить, пока не попросили.

## Комментарии

Пишем только если комментарий объясняет неочевидное поведение или сложный код:
почему именно так, какая здесь ловушка, почему иначе нельзя. Не пересказываем
код, не оправдываемся, не дублируем сигнатуру. Очевидное не комментируем.

## Тесты

Тест пишем, только если выполнены оба условия:

1. **Другой проверки нет.** Типы, линтер, контрастный гейт, пререндер, соседний
   тест. Тип вместо теста всегда лучше: `href: Path` ловит битую ссылку без
   единой строки тестов, потому что состав путей знает SvelteKit.
2. **Тест не хрупкий.** Правильный ответ известен заранее и не зависит от того,
   как названы классы, строки и файлы. Тест не лезет в `fs`, приватные API и
   структуру папок. Хрупкий тест меняется вместе с кодом — от него отказываются.

Лучше не написать тест вовсе, чем написать хрупкий. Тест, который проверяет
собственную вёрстку проекта, не ловит ничего.

Данные из `data/` на согласованность не тестируем: они статичны, разворачиваются
в компоненте и падать не умеют.
