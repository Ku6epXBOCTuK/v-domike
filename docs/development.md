# Разработка

Как запустить, как устроен репозиторий и что делать, когда хочется что-то
поменять. Правила оформления и текста — в [`design.md`](design.md), устройство
кода — в [`architecture.md`](architecture.md).

## Запуск

Нужен Node 22+ и pnpm. Версия Node проверяется строго (`.npmrc`:
`engine-strict=true`).

```sh
pnpm install
pnpm dev        # http://localhost:5173/v-domike/
```

### С телефона

`pnpm dev --host` поднимает сервер на всех интерфейсах и печатает адрес вида
`http://192.168.x.x:5173/v-domike/` — его и открывают с телефона в той же сети.
Так проверяют вёрстку на настоящем экране: safe-зоны из `env()` там нулевые,
пока не открыто standalone-приложение, поэтому нижняя навигация в браузере
телефона увидит только `env(safe-area-inset-bottom)`, а не верхний вырез.

По локалке не зарегистрируется service-worker и не поставится PWA: `http://` на
не-localhost адресе не secure context. Для этого нужен https — то есть хостинг.

| Команда             | Что делает                                 |

### Перед коммитом

```sh
pnpm check && pnpm lint && pnpm test
```

Три команды обязательны. `pnpm lint` включает `scripts/check-contrast.mjs`: он
читает `tokens.css`, разбирает обе темы и прогоняет зарегистрированные в нём
пары «текст/графика на фоне» по формуле WCAG, а затем инварианты токенов. Провал
роняет линт.

## Стек

SvelteKit 5 (runes) · TypeScript · `adapter-static` · `unplugin-icons` +
Iconify.

**Без Tailwind, без CSS-in-JS, без препроцессоров.** Только `<style>` в каждом
компоненте и дизайн-токены в `src/lib/styles/tokens.css`.

### Где лежит конфиг

`svelte.config.js` в проекте нет. Вся конфигурация SvelteKit передаётся прямо в
плагин из `vite.config.ts`:

```ts
sveltekit({
  compilerOptions: { runes: ({ filename }) => /* ... */, experimental: { async: true } },
  adapter: adapter(),
  experimental: { remoteFunctions: true },
})
```

Руны принудительно включены для всех файлов проекта (кроме `node_modules`).
`remoteFunctions` включены, но не используются.

## Меню

`src/lib/data/dishes.json` — источник правды: категории и блюда. Форму блюда
объявляет `dishes.ts`, а проверяет `scripts/check-dishes.mjs`: уникальность `id`
и названия, kebab-case, цена кратна десяти, `eta` вида «15–20 мин», тон из
списка, категория объявлена, файл снимка существует. Скрипт встроен в
`pnpm lint`, отдельно гоняется как `pnpm check:dishes`.

Добавил блюдо — напиши его в JSON и прогони `pnpm check:dishes`. `id` латиницей
в kebab-case и совпадает с именем файла: `image: "dishes/<id>.webp"`. **Пустой
`image` означает «снимка пока нет»**: `dishImage()` подставит
`dishes/placeholder.webp`, и пререндер не превратится в битую картинку. Блюда
без снимка печатает `pnpm check:dishes` в конце.

## Снимки блюд

Фотографии не кладут в `static/` руками — их кладёт **`pnpm images`**.

```sh
# 1. Копируем снимок в refs/dishes/ под именем блюда
#    refs/dishes/borsh.jpg, refs/dishes/tiramisu.png
pnpm images
```

Скрипт `scripts/make-dish-images.mjs` берёт всё из `refs/dishes/`, **режет по
центру до 600×682** и кодирует webp с качеством 0,8, кладёт в
`static/dishes/<id>.webp` и **проставляет `image` в `dishes.json`**. Кадр всегда
600×682, независимо от пропорций исходника: у соседних карточек иначе прыгает
высота, и `width`/`height` в разметке перестают совпадать с файлом. Каждый
снимок пишется в двух размерах: 600 px и `-450` рядом с ним, потому что карточка
на телефоне — 176 CSS px, а `srcset` в карточке и в миниатюре корзины раздаёт по
размеру. Новый размер добавляешь в `WIDTHS` — больше ничего трогать не надо.
Расширение любое из тех, что открывает браузер: jpg, jpeg, png, webp, avif, gif.
Исходники не трогает — тот же файл можно перезалить, если кадр не понравился;
если снимок у блюда уже был, он перезапишется, это штатный способ заменить
неудачную фотографию.

Имя файла обязано быть `id` существующего блюда. Ошибка в имени останавливает
скрипт **до** обработки: снимок, которому не соответствует `id`, в приложении
просто не показался бы. Список блюд, которым снимок ещё не достался, печатает
`pnpm check:dishes` — их `id` и нужно копировать в `refs/dishes/`.

### Откуда берутся снимки

`pnpm photos` набирает недостающие снимки сам — из карты
[foodiesfeed.com](https://www.foodiesfeed.com) (CC0):

```sh
pnpm photos     # скачать в refs/dishes/, записать refs/photo-sources.json
pnpm images     # перерезать и заменить картинки
pnpm review:photos   # пересобрать refs/dishes-review.md
```

Названия блюд в `dishes.json` русские, а слаги источника английские и
описательные, поэтому сверить их автоматически нельзя: подсказки написаны руками
в `scripts/dish-photo-hints.mjs`, по нескольку на блюдо, от точной к общей.
Сравнение слов целиком и обязательно подряд: «tom yam» в каталоге не встречается
ни разу, а «mushroom soup» — три раза, и без требования соседства одно слово
вроде «pasta» находит полузаготовку из макарон вместо блюда.

Две ловушки, из-за которых снимок может достаться не тому блюду, и обе лечатся в
скрипте:

- **Серия снимков с одного стола.** В каталоге есть кадры `-3`, `-5` и разные
  идентификаторы съёмки у одной и той же серии. Хвост слага отбрасывается, и
  снимки одной съёмки не достаются двум блюдам: файлы разные, хеши разные, на
  контактном листе это не видно.
- **Снимков в каталоге меньше, чем блюд в меню.** 3734 снимка против 365 блюд, и
  половины названий — такояки, кунафа, кимчи, хачапури — там нет вовсе. Если по
  подсказкам ничего не нашлось, снимок берётся по категории
  (`CATEGORY_FALLBACK`) и помечается в `refs/photo-sources.json` как `fallback`.

Поэтому набранное **смотрят глазами**: `pnpm review:photos` собирает
`refs/dishes-review.md` — список с галочками, картинкой и ссылкой на источник, с
пометкой «подбор по категории» там, где в каталоге не было даже намёка на блюдо.
Галочка в лишнем снимке означает «убрать»: удалить `static/dishes/<id>.webp` и
`-450` рядом, поставить блюду `"image": ""`. Исходники в `refs/dishes/` в git не
попадают — что там лежит, тем же `pnpm photos` набирается заново.

Тем же скриптом `pnpm images` рисуется `static/dishes/placeholder.webp` — купол
над блюдом, обведённый тонкой линией. Он прозрачный и домножается на подложку
карточки; подложка плейсхолдера — смесь тона с `--surface-sunken`, а не сам тон,
поэтому в тёмной теме карточка без снимка не светится светлым пятном.
Подробности — в [`design.md`](design.md). Правится рисунок в начале
`make-dish-images.mjs`, подложка — в `DishCard.svelte` и `DishThumb.svelte`; оба
места перерисовываются/пересобираются автоматически.

**Ни одна кухня не должна быть в приоритете или ущемлена.** Задача владельца —
меню со всего мира, а не копия «корейских дофамин-приложений»: корейские блюда
есть наравне с остальными, и в каждой категории их должно быть столько же,
сколько у любой другой крупной кухни.

## Иконки и манифест

`static/manifest.webmanifest` и иконки рядом с ним **генерируются**:
`pnpm icons` рендерит их из `refs/icon.jpeg` и пишет манифест заново. Правки в
`static/manifest.webmanifest` руками перетрутся — правится `refs/icon.jpeg` и
палитра, потом команда прогоняется снова.

Ссылка на манифест в `app.html` идёт через `%sveltekit.assets%`, поэтому
остаётся верной и в корне домена, и в подкаталоге `/v-domike/`.

## OG-картинка

`pnpm og` собирает проект, поднимает раздачу `build/` под `/v-domike` и рисует
`static/og.jpg` (2400×1260) из HTML: слева иконка из `refs/icon.jpeg` с
названием, справа настоящий экран приложения в `iframe`. Экран берётся из
сборки, а не рисуется руками, поэтому картинка повторяет то, что уедет на
хостинг: поменялась вёрстка или ассеты — прогони `pnpm og` ещё раз.

Цвета и шрифты композиции читаются из `tokens.css`, поэтому после смены палитры
картинка не разойдётся с приложением. Серьёзная зависимость одна: подпись
набирается системным серифом, и на машине без `Palatino Linotype` заголовок
нарисуется другим шрифтом.

Теги `og:*` и `twitter:card` лежат в корневом `+layout.svelte` и относятся ко
всем экранам сразу. `og:image` отдаётся относительным адресом из `asset()` —
спецификация требует абсолютный, но под относительным чаты и скраперы
подставляют адрес сами; если превью вдруг не придёт, первым делом заменяют на
полный.

## Скриншоты для README

`pnpm screenshots` собирает проект, поднимает раздачу `build/` и снимает 4
экрана в двух темах в `docs/images/`. Ровно то, что уедет на хостинг.

- Вьюпорт 390×920, `deviceScaleFactor: 2`, анимации выключены.
- Раздача живёт по базовому пути `/v-domike` — тем же, что и на хостинге.
- Тема ставится через `localStorage` **до** загрузки страницы, скрипт падает,
  если `data-theme` не применился.
- Корзина наполняется кликами перед уходом на `/order`: экран снимается таким,
  каким его видит человек. Скрипт не сеет `localStorage` — в каждом контексте
  storage пустой, иначе снимки зависели бы от прошлого прогона.
- Изменил вёрстку — пересними картинки, README показывает старую версию.

## Деплой

`adapter-static` пишет готовые HTML в `build/`: `/order` становится
`build/order.html`. Собирать и выкладывать нужно именно эту папку, на любой
статический хостинг, без Node на сервере.

Маршруты лежат плоско, поэтому хостинг должен отдавать `/order` как
`order.html`. На GH Pages это работает само, на Netlify и Vercel — из коробки.

Ссылки внутри приложения относительные (`./order`, `../profile`): их даёт
`resolve()`, типизированный `RouteId`. Приложение поэтому работает и в
подкаталоге хостинга, а опечатка в адресе падает на `pnpm check`.

### GitHub Pages

`paths.base = "/v-domike"` в конфиге SvelteKit — приложение лежит в подкаталоге
хостинга, и база объявлена явно. Побочный эффект: dev-сервер тоже отвечает под
`/v-domike/`, а в HTML ссылки остаются относительными (`./cart`,
`./dishes/ramen.webp`) — их даёт `resolve()` и `asset()`.

`adapter({ fallback: "404.html" })` отдаёт вместо 404 хостинга страницу
приложения: SvelteKit генерирует `404.html`, который грузит шелл и рендерит
`+error.svelte`. **Работает именно благодаря base:** без него страница грузила
бы скрипты от корня домена, где их нет, и человек увидел бы пустую страницу
вместо оформленной.

`.github/workflows/pages.yml`: пуш в `main` → `pnpm build` →
`actions/upload-pages-artifact` → `actions/deploy-pages`. Ручной запуск — кнопка
Run workflow на вкладке Actions. Отдельный `pnpm install` в шагах не нужен:
`pnpm/setup` ставит pnpm и Node и выполняет установку сам, с
`require-lockfile: true` — без `pnpm-lock.yaml` шаг упал бы, а не разрешил бы
зависимости из реестра.

Адрес: **`https://ku6epxboctuk.is-a.dev/v-domike/`**. Кастомный домен привязан к
Pages проекта, поэтому приложение лежит не в корне домена, а в подкаталоге
`/v-domike/`. Отдельный домен покупать не нужно: https Pages выдаёт сам, по
сертификату Let's Encrypt, `Enforce HTTPS` включён.

Чего воркфлоу не делает: не гоняет `pnpm check`, `pnpm lint` и `pnpm test` перед
выкладкой. Пока это не сделано, порядок «проверил локально → запушил» держится
на владельце.

## Известные проблемы

- **404 приходит от хостинга, а не от приложения.** `+error.svelte` есть: в dev
  и при настоящих ошибках он показывает страницу в оформлении приложения. Но
  `adapter-static` без `fallback` не знает про неизвестные пути — `/orderr`
  отдаст 404 самого хостинга. Хостинг определился (GitHub Pages), и лечится это
  одним `fallback: "404.html"` в адаптере: Pages подхватит файл сам. Пока не
  сделано — см. бэклог.
- **Предупреждение `adapter-static`**:
  `Reading config.kit inside adapters is deprecated`. Приходит изнутри адаптера,
  сборку не ломает. Наша форма конфига уже та, которой ждёт апстрим; ждём, пока
  приберут.
- **`src/lib/index.ts` пустой.** Работает как цель импорта для `#lib`, но
  экспортов не содержит.
- **`static/robots.txt` из скаффолда**, `Disallow:` пустой.
