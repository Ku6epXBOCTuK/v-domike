# Разработка

Как запустить, как устроен репозиторий и что делать, когда хочется что-то
поменять. Правила оформления и текста — в [`design.md`](design.md), устройство
кода — в [`architecture.md`](architecture.md).

## Запуск

```sh
pnpm install
pnpm dev        # http://localhost:5173/v-domike/
```

`pnpm dev --host` поднимает сервер на всех интерфейсах и печатает адрес вида
`http://192.168.x.x:5173/v-domike/` — его открывают с телефона в той же сети.
Так проверяют вёрстку на настоящем экране: safe-зоны из `env()` там нулевые,
пока не открыто standalone-приложение, поэтому нижняя навигация в браузере
телефона увидит только `env(safe-area-inset-bottom)`, а не верхний вырез.

По локалке не зарегистрируется service-worker и не поставится PWA: `http://` на
не-localhost адресе не secure context. Для этого нужен https, то есть хостинг.

## Команды

| Команда              | Что делает                                  |
| -------------------- | ------------------------------------------- |
| `pnpm dev`           | dev-сервер                                  |
| `pnpm dev --host`    | dev-сервер, доступный с телефона            |
| `pnpm build`         | сборка и пререндер всех страниц в `build/`  |
| `pnpm preview`       | локальный просмотр собранного сайта         |
| `pnpm check`         | `svelte-check` + тайпчек                    |
| `pnpm check:watch`   | то же в watch-режиме                        |
| `pnpm lint`          | prettier, eslint, **контраст и форма меню** |
| `pnpm check:tokens`  | только контраст и инварианты токенов        |
| `pnpm check:dishes`  | форма и снимки меню                         |
| `pnpm test`          | vitest                                      |
| `pnpm test:unit`     | тот же vitest в watch-режиме                |
| `pnpm format`        | prettier --write                            |
| `pnpm screenshots`   | скриншоты для README                        |
| `pnpm icons`         | пересобрать иконки и манифест из `refs/`    |
| `pnpm images`        | собрать снимки блюд из `refs/dishes/`       |
| `pnpm review:photos` | пересобрать `refs/dishes-review.md`         |
| `pnpm og`            | переснять OG-картинку из текущего `build/`  |

Перед коммитом:

```sh
pnpm check && pnpm lint && pnpm test
```

`pnpm lint` включает `scripts/check-contrast.mjs` (разбирает `tokens.css` и
прогоняет зарегистрированные пары по формуле WCAG, полупрозрачные поверхности
считает поверх родителя) и `scripts/check-dishes.mjs`. Провал роняет линт.

## Снимки блюд

Фотографии не кладут в `static/` руками — их кладёт **`pnpm images`**.

```sh
# снимок копируется в refs/dishes/ под именем блюда
# refs/dishes/borsh.jpg, refs/dishes/tiramisu.png
pnpm images
```

`scripts/make-dish-images.mjs` берёт всё из `refs/dishes/`, **режет по центру
под кадр карточки**, кодирует webp, кладёт в `static/dishes/<id>.webp` и
**проставляет `image` в `dishes.json`**. Кадр всегда одного размера независимо
от пропорций исходника: у соседних карточек иначе прыгает высота и
`width`/`height` в разметке перестают совпадать с файлом. Каждый снимок пишется
в двух размерах, потому что `srcset` раздаёт по размеру, а карточка на телефоне
намного меньше снимка. Новый размер добавляется в `WIDTHS`, больше ничего
трогать не надо. Расширение любое из тех, что открывает браузер: jpg, jpeg, png,
webp, avif, gif. Исходники не трогает — тот же файл можно перезалить.

Имя файла обязано быть `id` существующего блюда, иначе скрипт останавливается
**до** обработки: снимок, которому не соответствует `id`, в приложении просто не
показался бы. Блюда, которым снимок ещё не достался, печатает
`pnpm check:dishes` — их `id` и нужно копировать в `refs/dishes/`.

### Откуда берутся снимки

Источник — [foodiesfeed.com](https://www.foodiesfeed.com), всё снятое в
`static/` это CC0. Скрипта-дозагрузчика в проекте нет: снимки подбирались один
раз и лежат в репозитории. Цикл такой:

```sh
pnpm images          # перерезать refs/dishes/ и заменить картинки
pnpm review:photos   # пересобрать refs/dishes-review.md — список на ревью
```

Подбирать приходится руками: названия блюд русские, слаги источника английские и
описательные, сверять их автоматически нечем. Три ловушки, из-за которых снимок
достаётся не тому блюду:

- **Серия снимков с одного стола.** В каталоге есть кадры одного стола с разными
  идентификаторами съёмки. Хвост слага отбрасывается, иначе три карточки подряд
  показывают одно и то же блюдо: файлы разные, хеши разные, на контактном листе
  это не видно.
- **Слова надо сравнивать целиком и обязательно подряд.** «tom yam» в каталоге
  не встречается ни разу, а «mushroom soup» — три раза, и без требования
  соседства одно слово вроде «pasta» находит полузаготовку из макарон вместо
  блюда.
- **Снимков в каталоге меньше, чем блюд в меню, и половины названий там нет
  вовсе** — такояки, кунафа, кимчи, хачапури. Для таких блюд снимок брался по
  категории, и это видно на ревью.

Поэтому снимки **смотрят глазами**: `pnpm review:photos` собирает
`refs/dishes-review.md` — список блюд с галочками, чтобы пройти по меню и
отметить лишние. Галочка означает «убрать»: удалить `static/dishes/<id>.webp` и
`-450` рядом, поставить блюду в `dishes.json` `"image": ""`; что осталось без
снимка, покажет `pnpm check:dishes`.

Тем же скриптом рисуется `static/dishes/placeholder.webp` — купол над блюдом,
обведённый тонкой линией. Правки: рисунок в начале `make-dish-images.mjs`,
подложка в `DishCard.svelte` и `DishThumb.svelte`; оба места
перерисовываются/пересобираются автоматически.

**Ни одна кухня не должна быть в приоритете или ущемлена.** Задача владельца —
меню со всего мира, а не копия «корейских дофамин-приложений»: корейские блюда
есть наравне с остальными, и в каждой категории их столько же, сколько у любой
другой крупной кухни.

## Иконки и манифест

`static/manifest.webmanifest` и иконки рядом с ним **генерируются**:
`pnpm icons` рендерит их из `refs/icon.jpeg` и пишет манифест заново. Правки
руками перетрутся — правится `refs/icon.jpeg` и палитра, потом команда
прогоняется снова.

Ссылка на манифест в `app.html` идёт через `%sveltekit.assets%`, поэтому
остаётся верной и в корне домена, и в подкаталоге `/v-domike/`.

## OG-картинка

`pnpm og` собирает проект, поднимает раздачу `build/` под `/v-domike` и рисует
`static/og.jpg` из HTML: слева иконка из `refs/icon.jpeg` с названием, справа
настоящий экран приложения в `iframe`. Экран берётся из сборки, а не рисуется
руками, поэтому картинка повторяет то, что уедет на хостинг: поменялась вёрстка
или ассеты — прогони `pnpm og` ещё раз.

Цвета и шрифты композиции читаются из `tokens.css`. Серьёзная зависимость одна:
подпись набирается системным серифом, и на машине без `Palatino Linotype`
заголовок нарисуется другим шрифтом.

Теги `og:*` и `twitter:card` лежат в корневом `+layout.svelte` и относятся ко
всем экранам сразу. `og:image` отдаётся относительным адресом из `asset()` —
спецификация требует абсолютный, но под относительным чаты и скраперы
подставляют адрес сами; если превью вдруг не придёт, первым делом заменяют на
полный.

## Скриншоты для README

`pnpm screenshots` собирает проект, поднимает раздачу `build/` и снимает экраны
в двух темах в `docs/images/`. Ровно то, что уедет на хостинг.

- Раздача живёт по базовому пути `/v-domike` — тем же, что и на хостинге.
- Тема ставится через `localStorage` **до** загрузки страницы, скрипт падает,
  если `data-theme` не применился.
- Корзина наполняется кликами перед уходом на `/order`: экран снимается таким,
  каким его видит человек. Скрипт не сеет `localStorage` — в каждом контексте
  storage пустой, иначе снимки зависели бы от прошлого прогона.
- Изменил вёрстку — пересними картинки, README показывает старую версию.

## Деплой

`adapter-static` пишет готовые HTML в `build/`: `/order` становится
`build/order.html`. Выкладывать нужно именно эту папку, на любой статический
хостинг, без Node на сервере. Маршруты лежат плоско, поэтому хостинг должен
отдавать `/order` как `order.html`. На GH Pages это работает само, на Netlify и
Vercel — из коробки.

Ссылки внутри приложения относительные (`./order`, `../profile`): их даёт
`resolve()`, типизированный `RouteId`. Приложение поэтому работает и в
подкаталоге хостинга, а опечатка в адресе падает на `pnpm check`.

`adapter({ fallback: "404.html" })` отдаёт вместо 404 хостинга страницу
приложения: SvelteKit генерирует `404.html`, который грузит шелл и рендерит
`+error.svelte`. **Работает именно благодаря `paths.base`:** без него страница
грузила бы скрипты от корня домена, где их нет, и человек увидел бы пустую
страницу вместо оформленной.

### GitHub Pages

`paths.base = "/v-domike"` — приложение лежит в подкаталоге хостинга, и база
объявлена явно. Побочный эффект: dev-сервер тоже отвечает под `/v-domike/`, а в
HTML ссылки остаются относительными.

`.github/workflows/pages.yml`: пуш в `main` → `pnpm build` →
`actions/upload-pages-artifact` → `actions/deploy-pages`. Ручной запуск — кнопка
Run workflow на вкладке Actions. Отдельный `pnpm install` в шагах не нужен:
`pnpm/setup` ставит pnpm и Node и выполняет установку сам, с
`require-lockfile: true` — без `pnpm-lock.yaml` шаг упал бы, а не разрешил бы
зависимости из реестра.

Адрес: **`https://ku6epxboctuk.is-a.dev/v-domike/`**. Кастомный домен привязан к
Pages проекта, поэтому приложение лежит не в корне домена, а в подкаталоге
`/v-domike/`. Отдельный домен покупать не нужно: https Pages выдаёт сам, по
сертификату Let's Encrypt, `Enforce HTTPS` включён.

Чего воркфлоу не делает: не гоняет `pnpm check`, `pnpm lint` и `pnpm test` перед
выкладкой. Пока это не сделано, порядок «проверил локально → запушил» держится
на владельце.
