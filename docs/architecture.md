# Архитектура

Как устроено приложение и по каким правилам в нём писать. Документ про текущее
состояние кода, не про его историю.

Оформление, токены, тема, иконки и тексты — в [`design.md`](design.md). Запуск и
команды — в [`development.md`](development.md).

## Стек

SvelteKit 5 в режиме runes · TypeScript · `adapter-static` · `unplugin-icons` +
Iconify.

Ни Tailwind, ни CSS-in-JS, ни препроцессоров. Стили живут в `<style>` каждого
компонента, значения — в дизайн-токенах.

### Конфиг

Отдельного `svelte.config.js` нет: вся конфигурация SvelteKit передаётся в
плагин `sveltekit()` внутри `vite.config.ts` — адаптер, принудительный режим
рун, `experimental.async` и `experimental.remoteFunctions`. Тесты настроены там
же: `environment: node` и `expect.requireAssertions: true`.

## Слои

| Слой        | Что                           | Знает про приложение? |
| ----------- | ----------------------------- | --------------------- |
| `ui/`       | переиспользуемые примитивы    | нет                   |
| `app/`      | шелл, шапка, навигация        | частично              |
| `features/` | карточка блюда, карта, экраны | да                    |
| `routes/`   | роуты, компоновка             | да                    |

`ui/` не знает про блюда, курьеров и табы. Если примитив начал упоминать
приложение — он переезжает в `features/`.

Данные (`data/`) не содержат компонентов и импортов разметки: только значения и
строковые ключи. Маппинг строка → иконка живёт в компоненте, который её рисует.
Меню лежит в `data/dishes.json` — это данные, а не код, и держать его в JSON
удобнее: строки читаются и правятся без компиляции.

`data/dishes.ts` поверх JSON объявляет **форму** блюда: импорт JSON типизируется
как `string` на любое поле, поэтому компилятор не может ни подтвердить, ни
опровергнуть ни `category`, ни `tone`, ни имя снимка. Проверяет форму
`scripts/check-dishes.mjs` (встроен в `pnpm lint`): уникальность `id` и
названия, kebab-case в `id`, цена кратна десяти, `eta` вида «15–20 мин», тон из
списка, категория объявлена, снимок существует.

**Пустой `image` — не ошибка, а «снимка пока нет».** На его месте `dishImage()`
подставляет `static/dishes/placeholder.webp`, и пререндер не падает на
несуществующем файле: SvelteKit пререндерит и `<img>`, поэтому битая ссылка
роняет `pnpm build` целиком. Список блюд без снимка печатает `pnpm check:dishes`
в конце — это очередь владельца.

Отсюда же `dishImage()`: `AssetPath` — союз имён файлов, которые **есть** в
`static/`, а в JSON пока строка, поэтому внутри помощника стоит одно приведение
типа. Настоящая проверка — скрипт.

## Роуты

Четыре экрана — четыре настоящих маршрута, а не табы на `useState`:

| Маршрут      | Экран   |
| ------------ | ------- |
| `/`          | меню    |
| `/cart`      | корзина |
| `/order`     | заказ   |
| `/favorites` | любимое |
| `/profile`   | профиль |

`/cart` — корзина: список позиций с количеством, итог и оформление. `/order` по
замыслу не экран, а **распределитель по статусу заказа**:

| Статус          | Куда                |
| --------------- | ------------------- |
| заказ в пути    | экран доставки      |
| заказ доставлен | экран результата    |
| заказа нет      | редирект на `/cart` |

Приоритет у заказа: если человек после оформления снова зашёл в меню и что-то
добавил, таб «Заказ» всё равно показывает доставку, а не корзину.

Цикл заказа: **меню → `/cart` → доставка → результат → `/cart`**. «Хорошо» на
результате просто сбрасывает заказ (`clearOrder`), и правило «заказа нет —
уходим в `/cart`» само возвращает в начало цикла, поэтому отдельной навигации
для кнопки не нужно.

Решение принимается в `onMount`, до него не рисуется ничего: статус лежит в
`localStorage`, а страница пререндерена, поэтому на сервере его не угадать.
Заглушка здесь была бы враньём — карту и панель прибытия нечем нарисовать, а
решение приходит в том же кадре. Тик живёт в `+page.svelte` и обновляет `now`
раз в секунду: фаза считается из часов, поэтому таймер ничего не пишет в
хранилище, а экран получает фазу и остаток через пропсы.

Плюс два маршрута внутри профиля — `/profile/history` и
`/profile/notifications`. В `TABS` их нет: у табов есть строка в навигации, у
этих страниц её нет. Активным остаётся «Профиль», потому что `BottomNav`
помечает раздел и на вложенных путях. Точка на табе «Заказ» горит, когда есть
что показать: корзина не пуста или заказ уже оформлен.

URL шарится, работает кнопка «назад», каждая страница пререндерится отдельно,
навигация работает без JS. `TABS` в `state/app.svelte.ts` — единственный список
роутов с пунктами навигации, из него строится нижняя панель.

**Ссылки типизированы `RouteId` и разворачиваются через `resolve()`** — так
состав путей знает сам SvelteKit, и опечатка в адресе падает на `pnpm check`, а
не на глаз. **Файлы из `static/` достаются через `asset()`**, а не строкой:
`AssetPath` — это союз всех имён файлов в `static/`, поэтому опечатка в имени
снимка падает на `pnpm check` с подсказкой. Проверено: `dishes/ramen-omg.webp`
даёт ошибку `not assignable to type ... Did you mean "dishes/ramen.webp"?`.

Базовый путь объявлен явно: `paths.base = "/v-domike"` в `vite.config.ts`. Из-за
этого `resolve()` и `asset()` отдают адреса с `/v-domike`, а в HTML SvelteKit
оставляет их относительными (`./cart`, `./dishes/ramen.webp`) — приложение
продолжает работать в любом подкаталоге. Побочная выгода: страница `404.html` от
хостинга получает скрипты по базе, а не от корня домена.

Абсолютный путь от корня домена, написанный руками (`/dishes/ramen.webp`,
`href="/"`), — всегда дефект. На выложенном сайте это выглядит как «картинки не
грузятся», и `pnpm check` такое не ловит — ловит только подстановка.

`AppShell`, `AppHeader` и `BottomNav` живут в `+layout.svelte`, роуты рендерят
только свой контент. `prerender = true` стоит в `+layout.ts` и покрывает все
маршруты сразу.

## Состояние

`src/lib/state/app.svelte.ts` экспортирует:

- `createAppState()` — фабрика, нужна тестам для свежих экземпляров;
- `app` — синглтон приложения, им пользуются компоненты.

Синглтон обязателен: SvelteKit перехватывает клик по внутренней ссылке и делает
клиентскую навигацию, поэтому модуль не перезагружается и корзина переживает
переход между страницами. Своя фабрика в каждом роуте обнуляла бы корзину.

Корзина хранит **ссылки** на блюда из каталога, а не копии: строка это
`{ id, count }`, и на экране она разворачивается в `{ dish, count }` через
каталог. Поэтому цена и ETA не могут устареть, а `cartTotal` и `orderTotal`
считаются из каталога, а не хранятся. Старый формат корзины — список id, где
повтор означал количество, — один раз пересчитывается при чтении.

Оформленный заказ лежит отдельным слотом `{ lines, placedAt }`: `placeOrder()`
переносит состав и чистит корзину, поэтому корзина после оформления пустая, а
состав заказа ещё можно показать. Фаза заказа не хранится, а выводится из часов
(`orderPhase`): минуты не тикают в состоянии, поэтому закрытая вкладка и
перезагрузка ничего не ломают и разойтись фазы не могут.

Тема, корзина, избранное и заказ переживают перезагрузку: читаются из
`localStorage` при создании состояния, читаются и пишутся в `try/catch`. В
хранилище лежат только `id`: при сборке они снова разворачиваются в ссылки на
каталог, а всё, чего в каталоге нет, отбрасывается. Стартового избранного нет —
на первом заходе `/favorites` пустая, и это состояние ничем не отличается от
«сняли все отметки».

**Всё, что лежит в `localStorage`, читается на клиенте, а страницы
пререндерены.** HTML из `build/` собран с пустым состоянием, и на прямой
загрузке страницы он расходится с тем, что покажет клиент. Что с этим делать,
зависит от блока:

- `{#if}` чинится сам. Маркер ветки в разметке позволяет Svelte увидеть, что
  сервер выбрал другую ветку, вычистить её и построить нужную заново — чужие
  ноды не переиспользуются. Поэтому бейдж и пустое состояние едут тихо.
- `{#each}` не чинится: при гидрации он берёт серверские ноды **по позиции** и
  ключи не сверяет, так что карточка из пререндера остаётся на месте, а текст и
  фотография уезжают от неё.

Отсюда правило: **список, который сервер наполняет, обязан быть за скелетоном**
(`FavoritesTab` так и делает). Список, который на сервере всегда пуст, чинить
нечего: клиент просто пересобирает ветку целиком, и `{#if}` вокруг него гасит
расхождение. На `/cart` список позиций как раз такой — за `{#if}` по
`lines.length`, и это держится только на нём. Если кто-то уберёт условие или
начнёт рисовать строки всегда, список надо закрыть скелетоном, как избранное.

## Отрисовка меню

Меню — 365 блюд, и нарисованные все они стоили телефону слишком дорого. Замеры
на `Pixel 7` при `CPU ×4` и сети 1,6 Мбит/с, до и после:

|                          | было                | стало             |
| ------------------------ | ------------------- | ----------------- |
| HTML главной             | 570 КБ (26 КБ gzip) | 24 КБ (5 КБ gzip) |
| узлов в DOM при открытии | 5 952               | 181–309           |
| первая картинка          | 2 796 мс            | 1 184 мс          |
| прокрутка 20 000 px      | 6 004 мс            | 1 470 мс          |

Три решения, каждое мерялось отдельно.

**Окно отрисовки.** `src/lib/state/virtual-grid.svelte.ts` держит в DOM только
ряды у экрана, а место остальных занимают распорки-разделители
(`grid-column: 1 / -1`, иначе они заняли бы ячейку и сдвинули сетку). `MenuTab`
меряет отрисованные карточки и пересчитывает окно на `scroll`. Высота ряда не
константа — название занимает от одной до трёх строк, — поэтому меряем то, что
нарисовано, а непомеренные ряды считаем по среднему: разброс 259–309 px, оценка
ошибается меньше чем на ряд. Проверено спуском до конца и обратно: все 365 блюд
показываются, разрывов в сетке ноль, полоса прокрутки доезжает до последней
карточки.

Ловушка, на которую ушло время: первая версия считала верх окна как
`scrollY − top − OVERSCAN`, а низ как `from + viewport + OVERSCAN` — запас снизу
при этом обнулялся, окно оставалось в четыре карточки, и браузеру нечего было
готовить заранее. Правильно: `to = start + viewport + OVERSCAN`, где `start` —
экран в координатах сетки.

**Никакого `backdrop-filter` в карточке.** Он стоял на двух бейджах каждой из
365 карточек — 730 размытых слоёв, и каждый кадр прокрутки браузер пересчитывал
их все. Один бейдж в минус 30% времени прокрутки, поэтому убрали оба. Стекло
стало плотнее, `--surface-glass-flat` (0.94 вместо 0.85): без размытия фото
просвечивает и пачкает иконку. Оба бейджа проверяет контрастный гейт.
`BottomNav` и подпись на карте блюр оставили — это два элемента, а не 730.

**Фото отдаётся в два размера.** Карточка на телефоне — 176 CSS px, снимок был
600 px, то есть экрану с плотностью 2,6 уезжало в 1,7 раза больше пикселей, чем
нужно. `pnpm images` пишет `-450` рядом с основным файлом, карточка отдаёт
`srcset`, миниатюра в корзине — `sizes="56px"`. На экранах с плотностью до 2,5
браузер берёт 450 px, это −40% веса и вдвое меньше пикселей на распаковку;
плотные экраны по-прежнему берут 600. Пути в `srcset` собираются через
`asset()`: написанный руками пререндер разрешает относительно текущего маршрута,
а не базы, и сборка падает с 404.

**Плейсхолдер грузится не лениво и с высоким приоритетом.** Он один на всё меню
и весит 6 КБ, но в окне он вставал в очередь за тяжёлыми фотографиями и карточка
мигала пустым тоном. Фотографии при этом остались `loading="lazy"`.

Чего окно не делает: `Ctrl+F` не находит блюда, которых нет в DOM, и скринридер
читает список короче настоящего. Для меню на 365 позиций это приемлемо, для
каталога с поиском — уже нет.

**Пока фото едет, карточка показывает скелетон, а не пустой тон.** Окно
отрисовки создаёт карточку за 1200 px до экрана, и без заглушки меню выглядело
как сетка пустых квадратов. Текст при этом настоящий сразу — ждёт только снимок.
Пока он не приехал, блок медиа берёт `--surface-sunken`, тот же цвет, что у
`SkeletonCard`: тон блюда на пустом месте читается как «фото есть, но пустое» и
путается с едой на соседней карточке. Поверх — блик из общей утилиты `.sheen`,
которая заодно заменила копию анимации внутри `SkeletonCard`. Снимок из кэша
помечается готовым в `$effect` до первой отрисовки, иначе блик мигал бы на уже
загруженной карточке; при ошибке загрузки он тоже гаснет, чтобы не крутиться
вечно. Плейсхолдер блика не получает: купол и есть ответ для блюда без снимка, а
не состояние загрузки.

Две ловушки, на которые ушло время. Первая: `data-done={photoReady}` при `false`
рендерится как `data-done="false"`, а селектор `[data-done]` срабатывал всегда —
блик был невидим с первой отрисовки. Атрибут надо ставить как
`photoReady ? "" : undefined`, по образцу `data-empty` в этой же карточке.
Вторая: блик кладётся **поверх** снимка, а не под ним, потому что у фото
`mix-blend-mode: multiply` и подложка под ним должна быть ровной — анимированный
градиент под фотографией означал бы, что тонировка едет вместе с бликом.

## Офлайн

`src/service-worker.ts` кладёт в кэш весь шелл: файлы сборки, всё из `static/` и
все пререндеренные страницы. Стратегия cache-first, поэтому приложение
открывается целиком — включая экраны, на которые человек ещё не заходил.

Precache сделан через `cache.addAll` и это намеренно: одна недостающая страница
уронит установку целиком, и поломка будет видна в консоли, а не оставит половину
офлайна молча.

Имя кэша — `v-domike-<version>`, где `version` приходит из `$app/env` и меняется
на каждой сборке. Новая выкладка ставит новый service worker, тот перезаписывает
кэш и удаляет старый в `activate`. Обновление **молчаливое**: плашки «есть
обновление» нет, человек может один раз увидеть старую вёрстку и закрыть
вкладку.

**База берётся из `self.registration.scope`, а не из `$app/paths`.** Пути из
`$app/manifest` лежат относительно корня сайта, а приложение живёт в подкаталоге
хостинга; `resolve()` внутри service worker о базе не знает, и precache уехал бы
в корень домена — без единой ошибки. Scope регистрации и есть нужный подкаталог.
По той же причине страница регистрирует скрипт через
`new URL(resolve("/"), location.href)`: на вложенной странице
`/v-domike/profile/history` относительный `service-worker.js` попал бы в
`/v-domike/profile/`. Сама регистрация — в `onMount` корневого `+layout.svelte`,
в деве пропускается: скрипт там не собирается, и был бы 404 на каждой загрузке.

`src/service-worker.ts` **намеренно не исключён** из `tsconfig.json`. SvelteKit
хочет исключить его (worker и странице нужны разные DOM-библиотеки) и печатает
при сборке `"src/service-worker" should be added to the "exclude" array` — три
раза, по одному на окружение. С exclude файл выпадает из tsconfig-проекта, и
редактор собирает для него inferred project без ambient-модулей `$app/*`: в VS
Code `$app/env` не находится, а `pnpm check` файл не видит. Расходятся тут
только внимание к выводу и работоспособность редактора.

## Тесты

Правила — в [`AGENTS.md`](../AGENTS.md): тест пишется, только если его не ловит
тип или линтер и если он не хрупкий.

**Тест, который проверяет твою же вёрстку, не ловит ничего.** Полезен только
тот, где правильный ответ известен заранее и не зависит от того, как ты назовёшь
класс. Поэтому нет тестов вида «рендерит `data-tone="warm"`».

Отдельно: рендер-тесты на `svelte/server` **не видят обработчики** — в
SSR-разметке их нет вообще. Сломанный `onclick` они пропустят. Если понадобится
проверять клики, нужен браузерный раннер, а не `svelte/server`: он уже стоит для
скриншотов.

## Чего нельзя

- Сырые цвета, радиусы, тени и длительности вне `tokens.css`.
- `class` на иконках из `~icons`.
- Расширение `.svelte` без `.js` в импортах вида `#lib/...`.
- Ховеры и тени, определённые не через токен `--duration-*`.
- Мёртвые кнопки: элемент без обработчика и без ссылки — либо ведёт куда-то,
  либо не рендерится.
- `href: string` там, где адрес ведёт внутрь приложения: `RouteId` + `resolve()`
  проверяются типами, строка — нет.
- Путь к файлу из `static/` строкой: `AssetPath` + `asset()`.
- Путь от корня домена (`src="/…"` без `asset()`), если приложение лежит в
